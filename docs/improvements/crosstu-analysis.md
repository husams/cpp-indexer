# Cross-TU analysis via `clang::cross_tu` (exploratory)

`CrossTranslationUnitContext` is the machinery behind the static analyzer's
CTU mode. Status: **exploratory** — no current cidx use case requires it;
this file records what it offers and the conditions under which we would
adopt it.

## Recommendation

Keep this proposal deferred.  cidx's USR-keyed storage already supports
cross-translation-unit identity and graph queries without importing foreign
ASTs.  The extra artifact generation, disk footprint, and `ASTImporter` memory
growth are warranted only by a named analysis that needs a callee's body.

The prerequisite is an intra-procedural rule that cannot be expressed from the
stored graph and CFG facts alone.  If that arises, ship CTU as an explicitly
opt-in analysis prepass with bounded imports, recorded diagnostics, and
corpus-based disk/RSS limits—not as part of normal indexing.  Cross-TU
must-call analysis is a later extension, not the first CTU deliverable.

See the project-wide ordering and gates in [README.md](README.md).

## What it provides

- **External definition lookup** — given a USR, find which other TU holds the
  *definition* of a function/variable only declared in the current TU.
- **Definition index** — a prebuilt USR → AST-file mapping, generated by the
  `clang-extdef-mapping` tool over `compile_commands.json`.
- **On-demand AST import** — loads the other TU's serialized AST (`.ast`
  file) and merges the definition into the current `ASTContext` via
  `ASTImporter`, so a body defined elsewhere can be walked as if local.
- **Import controls** — limits on how many TUs to load, clean reporting of
  import failures.

## Why we don't use it for indexing

Our storage layer already links symbols across TUs by USR at query time —
the right design for a batch indexer. CrossTU solves a different problem:
*in-memory* cross-TU access during a single analysis pass, and it requires
pre-dumping every TU's AST to disk, which is expensive at llvm-project scale
(3.5k TUs) in both time and storage.

## When it becomes worth adopting

Only when a `cidx analyze` rule needs a callee's *body* (not just its graph
edges) from another TU. Candidate rules:

1. **Cross-TU must-call / CFG reachability** — extend the CFG-based
   must-call relation ([cfg-analysis.md](cfg-analysis.md), item 5) through
   calls into other TUs.
2. **Cross-TU purity analysis** — decide whether a function is pure when its
   callees are defined in other TUs.
3. **Inline-expansion facts** — record what an out-of-TU callee reads/writes
   for escape or side-effect analysis.

## Adoption sketch (when triggered)

- Generate the extdef map and per-TU `.ast` dumps as an **opt-in analysis
  prepass** (`cidx analyze --ctu`), never as part of normal indexing.
- Budget disk (AST dumps for llvm-project will be tens of GiB) and bound
  imports per TU; measure RSS — `ASTImporter` merges grow the destination
  context.
- Import only function bodies the active rule asks for; discard contexts
  between TUs.

## Decision

Do not adopt now. Revisit when the first body-across-TU analysis rule is
proposed; until then, USR-linking in storage covers all cross-TU queries.
